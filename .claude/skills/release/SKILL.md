# Выпуск версии

Аргумент: новая версия `X.Y.Z` (без «v»). Если её нет — спроси, предложив следующую минорную.
Текущая версия — в `pyproject.toml` (`version = …`). Номер должен быть больше текущего: выпуск той же или
меньшей версии перезапишет сборки в CI под старым именем.

Выпуск публичный и необратимый по сути (пуш в `main`, сборки в CI), поэтому шаги идут строго по порядку:
пока не прошли тесты — не коммить, пока не запушено — не запускай сборку.

## 1. Номер версии — во всех шести местах

Найди старый номер: `git grep -n "<старая>" -- . ':!data'` (если git ругается на длинные пути Java-файлов
виджета — `git -c core.longpaths=true grep …`). Он записан в:

| Файл | Что |
|------|-----|
| `pyproject.toml` | `version = "X.Y.Z"` |
| `build.bat` | `--product-version "X.Y.Z" --file-version "X.Y.Z.0"` |
| `BUILD.md` | тот же пример команды |
| `.github/workflows/build.yml` | `--product-version "X.Y.Z"` в задаче macOS |
| `ui/screens/settings.py` | «F1 Analytics Hub X.Y» в блоке «О приложении» — короткий номер, полный поиск его не найдёт |
| `CHANGELOG.md` | новый раздел `## X.Y.Z (ГГГГ-ММ-ДД) — <суть одной фразой>` сверху |

Тегов в репозитории нет, поэтому начало диапазона ищи по прошлому выпуску:
`git log --oneline --grep "^Release" -1`, а если таких коммитов нет — по коммиту, где менялась строка
`version` в `pyproject.toml` (`git log -1 --format=%h -S'version = "<старая>"' -- pyproject.toml`).
CHANGELOG пиши по `git log <начало>..HEAD --oneline`: что изменилось для пользователя, обычным языком,
по-русски, жирным — суть пункта, как в прошлых разделах. Правки тестов, CI, документов и рефакторинг не
перечисляй — пользователь их не увидит; исправленные ошибки — перечисляй, это ему важно.

Правь эти строки инструментом Edit, а не `sed`: у части файлов в рабочей копии концы строк CRLF, и `sed`
переводит весь файл в LF — в diff получается шум на каждой строке.

После правок `git grep -n "<старая>" -- . ':!data' ':!CHANGELOG.md'` должен быть пустым, а
`git grep -n "Hub <старая X.Y>"` — тоже.

## 2. Проверки и коммит

```bash
venv/Scripts/ruff.exe check .
F1_HUB_LOG=off venv/Scripts/python.exe -m unittest discover -s tests -t .
```

Прогон эмулятора Android ищет на экране надписи (`tools/android_smoke.py`). Если с прошлого выпуска
менялись заголовки, кнопки или пункты меню — сверь их с ожидаемыми там надписями до запуска CI: иначе сборка
упадёт через 20 минут из-за самой проверки.

Коммит `Release X.Y.Z` (хук проекта ещё раз прогонит тесты), пуш в `main`.

## 3. Сборка всех платформ

Токен gh — из менеджера учётных данных git, не печатать его:

```bash
export GH_TOKEN=$(printf "protocol=https\nhost=github.com\n\n" | git credential fill | sed -n 's/^password=//p')
gh workflow run build.yml -f version=vX.Y.Z
```

Дождись завершения в фоне (`gh run watch <id>`), не опрашивай вручную. Журналы задач:
`gh api --allow-escape-sequences repos/Artist-huh/f1-analytics-hub/actions/jobs/<job id>/logs`.
Строки результатов проверок запуска:
- Windows и macOS (`tools/desktop_smoke.py`): `запуск: первая запись в журнале через N с …`
- iPhone (`tools/ios_smoke.py`): `iPhone: приложение запущено и работает 120 с …`
- Android (`tools/android_smoke.py`): `страница пилота: открылась поверх списка …`; при сбое — `ПРОБЛЕМЫ:`

Упавшую задачу разбери по журналу и почини до выпуска, а не после. Если упала сама проверка
(например, она ждёт старую надпись), чинить надо проверку — скажи об этом прямо.

## 4. Итог пользователю

Таблица: платформа / сборка / проверка запуска (с числами из журналов) и ссылка на прогон.
Релиз на GitHub (`gh release create vX.Y.Z`) — только если пользователь попросит: он публичный, и задачи
CI выложат к нему файлы сборок.
